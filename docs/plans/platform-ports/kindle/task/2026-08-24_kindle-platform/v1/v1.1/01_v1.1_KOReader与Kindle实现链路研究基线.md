# v1.1 KOReader 与 Kindle 实现链路研究基线

**职责**: 固定 K0–K3 开工前必须核验的上游项目、源码链路和研究输出。首台设备的 Stock → Homebrew-ready 路线已经由 `20` 单独冻结；本文主要负责设备准备完成后的 KOReader/Kindle substrate 源码核验。

---

## 1. 已确认的成熟能力来源

Kindle Reference Port 优先复用：

```text
KOReader / koreader-base
→ Kindle device detection / screen / input / lifecycle knowledge
→ Lua/LuaJIT environment
→ UIManager / widgets
→ ReaderUI

FBInk
→ verified framebuffer / E-Ink display mechanisms

Kindle OS / validated Homebrew mechanisms
→ lifecycle / power / frontlight / install / launch integration

KPM
→ modern jailbreak 后首台开发机的现成 Homebrew package infrastructure
→ K6 时用于 Baga Platform 正式 native package management

sh_integration
→ first-phase Kindle Home entry

MRPI / legacy envelope
→ only where KPM is unavailable or unvalidated

KindleTool / Kindle SDK / toolchain
→ build/package/native-target tooling
```

这些组件的角色以 Kindle Architecture Freeze、Kindle Adapter Standard 与 `20` 的首台设备 route 为准。

---

## 2. Batch 0 与 Batch 1 的职责分离

```text
Batch 0
→ 真实 stock 5.16.3 开发机保护、WinterBreak2、Homebrew-ready Gate
→ 不承担 KOReader 源码深度研究

Batch 1
→ current repo / upstream source verification
→ KOReader/koreader-base/FBInk pin 候选
→ kindlehf target、bootstrap、device/input/lifecycle 源码定位
```

不得因为 Batch 0 已经完成 jailbreak，就把“设备能跑 Homebrew”误认为“Baga pinned KOReader substrate 已经研究/锁定”。

---

## 3. Batch 1 必须核验的 KOReader 启动链

不得仅依赖历史描述。Batch 1 必须在准备 pin 的 KOReader commit 中定位并记录：

```text
Kindle launch script / environment setup
reader.lua or equivalent main entry
setupkoenv or equivalent environment setup
Device construction
screen initialization
input initialization
CanvasContext / UI foundation
UIManager initialization
FileManager / ReaderUI selection
PluginLoader invocation points
shutdown / exit path
```

研究输出必须回答：

1. direct Baga private entry 最早可以在哪个稳定点接入；
2. 接入时哪些 KOReader 初始化已经完成；
3. 如何避免 FileManager / Plugin UI 暴露；
4. clean exit / relaunch 怎样复用现有 shutdown；
5. local patch 对未来 KOReader 升级的维护面有多大。

---

## 4. Batch 1 必须核验的 Kindle Device 链

需要定位并保存源码路径/符号：

```text
Kindle Device implementation
screen backend selection
input device/event handling
model / firmware detection
suspend / wake / screensaver events
power handling
frontlight when applicable
kindle-legacy / kindle / kindlepw2 / kindlehf build target definitions
```

当前首台设备 firmware = 5.16.3。KindleModding Kindle SDK 当前把 firmware `>=5.16.3` 映射为 `kindlehf`，但 Batch 1/3 仍须从实际 toolchain/build 与真机证据确认。

K2 Adapter 不重新研究“从零怎样操作 Kindle 硬件”，而从这些成熟实现中寻找最薄的 Baga normalization 层。

---

## 5. FBInk 研究要求

如果 Display 路径需要 FBInk，Batch 1/3 必须记录：

```text
pinned source/commit
license
Kindle target support
KOReader/koreader-base 是否已包含或绑定该能力
Baga 是否需要额外 binding
额外 binding 的 ABI / build cost
适用于哪些 profile / firmware
```

原则：如果 KOReader 已经安全封装所需 display 行为，不为了“直接调用 FBInk”额外制造一层；只有 profile/refresh 证据表明更合适时才使用。

---

## 6. KPM / sh_integration 研究时机

首台开发机通过 modern WinterBreak2 route 后，KPM 应作为 Homebrew-ready Gate 的一部分被验证可用。

但必须区分：

```text
Batch 0
→ 验证开发机已经具备 KPM

K6 / Batch 9
→ 冻结 Baga Platform `.kpkg` 产品 packaging / install / update / uninstall
```

因此 KPM 的“存在性”不是 K6 才首次获得；K6 研究的是 Baga product package integration。

K1 仍不依赖用户通过 KPM 安装的任意 KOReader 版本。Baga 使用自己 pin 的 KOReader/koreader-base component set。

---

## 7. Jailbreak / bootstrap 研究边界

首台设备的 jailbreak 当前已由 `20` 固定：

```text
5.16.3 stock
→ OTA-safe preparation
→ WinterBreak2 after Wizard confirmation
→ KPM/OTA-block verified Homebrew-ready
```

这个手动 route 是 Reference Development Device 准备步骤，也将成为未来 K7 Route DB 的 evidence 来源。

它仍然**不进入**：

```text
Device Adapter Contract
Platform Core
KOReader substrate API
IKP contract
```

K7 才把已经验证的 route 自动化成：

```text
exact model + firmware + state
→ Installation Route record
→ verified transition to Homebrew-ready
```

任何 route 的内部 exploit/tool detail 都不能变成 Baga Device Adapter Contract。

---

## 8. 研究证据格式

Batch 1 研究结果至少记录：

| 项目 | 必须记录 |
|---|---|
| upstream | repository + commit/tag |
| source path | 精确文件路径 |
| symbol/entry | 关键函数/module/entry |
| role | Baga 哪个子系统使用 |
| license | upstream license |
| local patch | 是否需要、patch 目的 |
| device target | `kindlehf` 等 |
| evidence | build/log/device result |
| uncertainty | 尚未确认的事实 |

不得把推测写成已验证 upstream fact。

---

## 9. K1 direct-entry 研究默认

当前默认不是开放选型，而是验证：

```text
pinned KOReader bootstrap
→ direct Baga private entry
→ baga/bootstrap.lua
→ Baga-owned surface
```

类似 `--baga-app <app-id>` 的参数名只是内部实现细节，可以在源码核验后调整。

`.koplugin` 仅保留为 fallback research path。只有 direct entry 出现可复现 blocker 并形成证据时才重新评估。
