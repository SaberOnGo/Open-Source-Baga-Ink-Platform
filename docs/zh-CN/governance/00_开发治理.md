## 0. 目的

本文规定 Baga Ink 如何保存长期项目事实、组织 Standards / Design / Plans / Status / Reference Apps、管理 Branch / Pull Request，以及支持独立 Contributor 与 AI Agent 持续协作。

核心原则：

> **`main` 是长期事实来源。**

> **这个 Public Repository 中所有被 Git 跟踪的文档都属于公开材料。**

> **公开文档面向 Repository 用户、Contributor、Implementer、OEM Engineer、Reviewer 及其他第三方，不是私人项目讨论的聊天记录。**

---

## 1. `main` 的地位

`main` MUST 保存计划公开且长期有效的项目状态，包括按实际适用范围：

- Approved Standards；
- Approved Design；
- Reference Apps / Architecture Freeze；
- Current Project Status；
- Implementation Plans；
- Machine-readable Spec / Schema / Test Vector；
- Public / Reference Implementation；
- Tests / CI；
- 计划在该 Repository 中公开的 Platform / SDK / Tooling Source；
- Governance / Contributor Rules；
- Licensing、Third-party Provenance 与 Release Evidence。

第一方 Proprietary Product 与 Confidential Commercial Material 不要求存放在这个 Public Repository 中。

如果一个应当公开的技术结论只存在于 Feature Branch、Draft PR Discussion、Issue Comment、Chat Transcript 或 Private Notes，它还没有成为长期 Public Project Knowledge。

## 3. Public Repository Writing Rule

公开 / 私密属性由 Repository Visibility 与 Git Tracking 决定，不由文档目录名称决定。

因此，这个 Public Repository 中所有被 Git 跟踪的正文都必须适合第三方公开阅读，包括：

```text
README Files
CONTRIBUTING Files
AGENTS.md
COMMERCIAL_LICENSE Files
docs/en/
docs/zh-CN/
docs/plans/
Platform Port Task Designs
AI Execution Prompts
其他被 Git 跟踪的 Markdown Documentation
```

Public Repository Prose MUST：

- 面向真实 Public Audience，或者以 Project / Organization 的正式口吻陈述 Policy；
- 区分 Normative Requirement 与 Informative Rationale；
- 直接描述 Architecture、Implementation Plan、Compatibility、Licensing 与 Project Status；
- 在没有 Private Conversation 的情况下仍然能够独立理解；
- 不依赖作者个人上下文或私人决策讨论。

Public Repository Prose MUST NOT 包含：

- 对 Repository Owner 的聊天式回复；
- 只有结合历史聊天才能理解的“前面 / 刚才 / 上面讨论”类表达；
- 针对受众心理的私人策略判断，例如猜测某种措辞是否会让用户或厂商反感、害怕、愿意或不愿意参与；
- Confidential Monetization Strategy、Negotiation Tactics、Internal Pricing Logic 或未公开 Business Priority；
- `我建议`、`我们认为` 等把私人咨询过程直接带入公开政策正文的表达；项目要求和设计理由应直接写成 Policy、Requirement 或明确 Rationale。

面向正式 Public Role 的 Normative Instruction 属于正常公开文档，例如：

```text
Contributor MUST 运行 Validator。
OEM Port SHOULD 提供可复现 Compatibility Evidence。
Task Design MUST 定义 Acceptance Criteria。
```

`docs/plans/` 可以使用更直接的 Operational Engineering Language，但仍然是公开文档，必须满足同一 Publication Standard。

Confidential Material 应位于 Public Git Tracking 之外，例如本地被忽略的 `private/` 目录或独立 Private Repository。

Repository Validation：

```text
python3 tools/check_public_writing.py
```

## 4. 文档类型

不同文档类型回答不同问题：

```text
Baga Ink MUST 是什么
→ docs/<locale>/standards/

一个子系统怎样设计以及设计理由
→ docs/<locale>/design/

Reference App / Reference Platform 怎样验证 Standards
→ docs/<locale>/reference-apps/

项目当前处于什么状态
→ docs/<locale>/status/

Contributor 如何协作、项目怎样治理
→ docs/<locale>/governance/

Approved Design 怎样实施和验证
→ docs/plans/
```

`docs/plans/` 是公开 Operational Engineering Material，不要求每份 Task Design / AI Execution Prompt 都做多语言镜像；但外部 Implementer 需要依赖的 Stable Contract 不能只存在于 Platform Port Task 中，MUST 进入适当的 Standards / Design / Reference Apps / Governance / Status。

## 5. Branch / PR 生命周期

Feature Branch MAY 用于短期开发隔离、TDD Intermediate State、PR Review、CI Validation 与临时 Refactoring Work。

Feature Branch MUST NOT 用于长期保存 Architecture Decision、Current Status、Roadmap、Compatibility Matrix、Hidden Requirement 或只有一个 Contributor / AI Agent 知道的上下文。

标准流程：

```text
main
  ↓
short-lived branch
  ↓
implementation + tests + docs
  ↓
Pull Request
  ↓
Required CI Checks
  ↓
merge main
  ↓
delete branch
```

`main` 受 GitHub Ruleset 保护。Repository Change 遵守当前配置的 PR / CI 要求。

---

## 6. PR 的职责

PR 用于 Review、Diff Inspection、CI、Discussion 与可审计的 Construction History。

PR 不是 Current Project State Database。

Merge 后，当前 Public Fact MUST 进入适当的：

```text
Code
Tests
Machine-readable Specs
Standards / Design / Reference Apps
Status / Plans
```

未来 Maintainer 应能够在不阅读历史 PR Conversation 的情况下恢复当前 Public Architecture。

## 8. AI / Automation Rules

AI Agent 在这个 Repository 中工作时 MUST：

1. 以 `main` 为 Baseline；
2. 首先读取根目录 `AGENTS.md`；
3. 选择英文或中文 Documentation Index；
4. 使用 `docs/localization/catalog.json` 获取 Public Document Identity 与 Counterpart Mapping；
5. 阅读任务相关 Standards / Design / Reference App / Plan；
6. 不从历史 Branch 或 Private Conversation Context 推断当前 Architecture；
7. 通过适用 Repository Validator / CI；
8. 重要工作完成后更新 Status / Evidence；
9. 对所有新建或修改的 Tracked Documentation 应用 Repository-wide Public Writing Rule。

AI MUST NOT 为了让 Invalid Work 通过而削弱 Validator、扩大 Allowlist、修改 Required Check Name 或绕过 Governance。

## 9. Platform Port 大规模工程资料

`docs/plans/platform-ports/` 采用 High-scale Task Design / Execution Prompt Model，因为一个 Device Family 可能需要大量实施与验证 Task。

核心结构：

```text
platform-port/
├── task/
└── execution-prompts/
```

规则：

```text
docs/plans/platform-ports/0000_平台移植计划目录与文件命名规则_Baga-Ink-Platform-Port-Plan-Naming.md
```

Kindle Port 还需要遵守平台自己的 Task / Execution Prompt Guide。

这些 Plans 是公开 Operational Engineering Context。它们不会因为属于 Implementation Work Area 而变成 Private Material。

## 10. Draft → Stable

Standard 不能仅因为 Prose Complete 就进入 Stable。

对于 Executable Protocol，Stable Gate SHOULD / MUST（按 Governing Standard 定义）包含：

```text
Schema Validation
Canonical Test Vectors
Negative Corpus
Reference Implementation
Independent Implementation / Verifier
Cross-language Compatibility
End-to-end Tests
Device / Platform Evidence
CI / Conformance
```

Device Compatibility 还必须包含相关 Adapter Contract Tests / BICTS Evidence。

---

## 11. Device Adapter / OEM Port 治理边界

Device Adapter Contract 定义一个 Device Port 接入 Baga Ink 必须提供什么。

它不要求重新实现 OS、Vendor SDK、Homebrew Ecosystem 或成熟 Open-source Component 已经提供的能力。

Concrete Device Port SHOULD 尽量薄，集中处理 Device-family Difference，例如：

```text
Model / Firmware Differences
Capability Detection
Device Profile
Quirk Set
Error / Event Normalization
```

Reader/UI Framework、Installation Route、KPM/MRPI 与 Build Tooling 不因为“与设备有关”就属于 Device Adapter Root Contract。

## 12. License 与 Third-party Provenance

当前授权入口：

```text
LICENSE
docs/zh-CN/governance/02_Baga-Ink授权策略.md
COMMERCIAL_LICENSE.zh-CN.md
LICENSE_HISTORY.md
THIRD_PARTY_NOTICES.md
```

Baga 自研 Platform / OEM 侧软件遵守当前适用 Project License 或明确的 File / Directory Override。历史 Apache-2.0 Grant 由 `LICENSE_HISTORY.md` 记录。

第三方 Code / Component 保持上游 License。Baga Community / Commercial License 不重新许可 KOReader、FBInk、KPM 或其他上游项目。

可分发产品 MUST 记录适用 Dependency Version、Provenance、License 与 Local Modification。GPL / AGPL 以及其他 Redistribution Obligation 属于 Release Gate。

## 13. Commit / Tag / Release

Commit Subject SHOULD 使用英文并描述实际 Change，例如：

```text
docs: update device adapter standard
spec: add publisher identity schemas
feat: add IKP signature verifier
test: add invalid IKP corpus
```

Tag / Release 标记正式 Baseline，例如：

```text
standards-v0.1
ikp-v1.0
platform-v0.1
sdk-v0.1
```

历史状态通过 Commit / Tag / Release 恢复，不依赖 Permanent Feature Branch。

---

## 14. Completion Checklist

重要 Task 完成前根据实际范围确认：

```text
[ ] Implementation 已进入 Reviewed Change
[ ] 相关 Tests / CI PASS
[ ] Architecture Change 已进入 Governing Standard / Design
[ ] External Dependency Fact 已进入 Public Documentation
[ ] Current State 已进入 Status
[ ] 必要 Compatibility / Device Evidence 已记录
[ ] Branch 不包含 main 之外唯一的长期 Public Knowledge
[ ] License / Third-party Provenance 有效
[ ] Tracked Documentation 满足 Public Writing Rule
```

---

## 15. 最终原则

> **`main` 中的 Code + Machine Specs + Tests + Approved Public Documentation 定义 Baga Ink 的公开项目状态。所有 Tracked Document 都面向外部 Repository Audience；Confidential 或 Private-strategy Material 留在 Public Repository 之外。**
