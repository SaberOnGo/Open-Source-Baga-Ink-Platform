# Baga Ink 开发治理

> **文档级别：项目治理规范**  
> **Document ID：`governance.00`**  
> **语言：简体中文（`zh-CN`）**  
> **状态：Governance Baseline v0.3**  
> **日期：2026-08-23**

---

## 0. 目的

本文规定 Baga Ink 如何保存长期项目事实、如何组织 Standards / Design / Plans / Status / Reference Apps、如何使用 Branch / Pull Request、如何让人类和 AI 在没有历史聊天上下文的情况下继续开发。

最重要的原则：

> **`main` 是长期事实来源；短期 Branch 是施工脚手架，不是项目知识库。**

同时，Baga Ink 是国际化项目：

> **公共长期文档按 Locale 维护；协议、API、Schema、代码和测试仍然只有一套。**

---

## 1. `main` 的地位

`main` MUST 保存所有长期有效内容，包括：

- 当前批准的 Standards；
- Approved Design；
- Reference Apps / Architecture Freeze；
- 当前 Project Status；
- Implementation Plans；
- Machine-readable Spec / Schema / Test Vector；
- Reference / Independent Implementation；
- Tests / CI；
- 正式 Platform / SDK / Client / Market 源码；
- Governance / Contributor Rules；
- 许可证、第三方来源与发行证据。

如果一个重要结论只存在于：

```text
聊天记录
Feature Branch
Draft PR 描述
Issue 评论
个人笔记
AI 临时上下文
```

那么它还没有成为项目长期知识。

---

## 2. 公共文档的正式目录

公共、长期、外部开发者会依赖的正文统一按语言放置：

```text
docs/en/
docs/zh-CN/
```

公共类别：

```text
standards/
design/
reference-apps/
governance/
status/
```

同一个 Document Number / Document ID 的英文版和中文版只是同一文档的不同语言版本，不得演变为不同 Protocol / Architecture。

国际化具体规则见：

```text
docs/zh-CN/governance/01_文档国际化与本地化规范.md
docs/localization/catalog.json
docs/localization/terminology.json
```

历史混合语言目录目前只作为 Migration Zone；新增公共文档不得继续写入旧目录。

## 3. 不同文档类型回答不同问题

```text
Baga Ink MUST 是什么
→ docs/<locale>/standards/

一个子系统准备怎样实现、为什么
→ docs/<locale>/design/

Reference App / Reference Platform 如何验证标准
→ docs/<locale>/reference-apps/

项目现在真正做到哪里
→ docs/<locale>/status/

贡献者如何协作、项目如何治理
→ docs/<locale>/governance/

已经确定的设计下一步怎样施工
→ docs/plans/
```

`docs/plans/` 是工程施工区，不要求把几千份 Task Design / AI Execution Prompt 全部翻译成多语言。

但是：

> **任何外部实现者长期必须依赖的稳定结论，都不能只存在于某个中文 Task / Prompt 中；必须提升回 Public Localized Docs。**

## 4. Branch 与 PR

Feature Branch MAY 用于：

- 短期开发隔离；
- TDD 的 RED 中间状态；
- PR Review；
- CI 验证；
- 危险重构的临时保护。

Feature Branch MUST NOT 用于长期保存：

- Architecture Decision；
- 当前 Status；
- Roadmap；
- Compatibility Matrix；
- 隐藏需求；
- 只有某个 AI 知道的上下文。

标准生命周期：

```text
main
  ↓
short-lived branch
  ↓
implementation + tests + docs
  ↓
Pull Request
  ↓
Required CI Checks
  ↓
merge main
  ↓
delete branch
```

`main` 已通过 GitHub Ruleset 保护。不得以管理员便利为理由绕过正常 PR / CI 流程。

---

## 5. PR 的职责

PR 用于：

- Review；
- Diff；
- CI；
- Discussion；
- 可审计的施工历史。

PR 不是当前项目状态数据库。

PR 合并后，当前事实必须已经进入：

```text
代码
测试
Machine Spec
Standards / Design / Reference Apps
Status / Plans
```

未来维护者不应该必须阅读历史 PR 才能理解项目当前状态。

---

## 6. Status 必须集中维护

当前中文版状态入口：

```text
docs/zh-CN/status/00_当前项目状态.md
```

英文版：

```text
docs/en/status/00_baga-ink-project-status.md
```

重要 Milestone 改变时 MUST 更新 Status。

至少记录：

- Completed；
- In Progress；
- Next；
- Known Gaps；
- Draft / Stable 边界；
- Verification Evidence；
- 当前 Compatibility Claim 边界。

禁止让“现在做到哪里”只能从 Commit、Branch 或聊天推断。

---

## 7. AI / Automation 工作规则

新的 AI Agent MUST：

1. 以 `main` 为基线；
2. 首先读取根目录 `AGENTS.md`；
3. 选择英文或中文 Documentation Index；
4. 通过 `docs/localization/catalog.json` 找到当前有效 Public Doc 路径；
5. 再读取与任务相关的 Standards / Design / Reference App / Plan；
6. 不扫描历史 Branch 来猜当前架构；
7. 不因为文件或 Branch 看起来较新就认为它更权威；
8. 结构性修改必须通过仓库 Guard / CI；
9. 重要工作完成后更新 Status / Evidence。

AI MUST NOT 为了让自己的错误目录或文件名通过而削弱 Validator、扩大 allowlist、改掉 Required Check 名或绕过 Governance。

## 8. Platform Port 大规模任务资料

`docs/plans/platform-ports/` 采用独立的高规模任务治理，因为单个平台可能有几百个 Task、几千份 AI Execution Prompt。

核心结构：

```text
platform-port/
├── task/
└── execution-prompts/
```

详细规则见：

```text
docs/plans/platform-ports/0000_平台移植计划目录与文件命名规则_Baga-Ink-Platform-Port-Plan-Naming.md
```

Kindle 还需遵守该目录自己的 Task / Execution Prompt Guide。

这些计划资料是工程上下文，不是公开 Protocol Authority。

## 9. Standard 从 Draft 到 Stable

不得因为 Markdown “写完了”就把 Standard 标记为 Stable。

对于可执行协议，Stable Gate SHOULD / MUST（按对应 Standard 定义）包含：

```text
Schema Validation
Canonical Test Vectors
Negative Corpus
Reference Implementation
Independent Implementation / Verifier
Cross-language Compatibility
End-to-end Tests
Device / Platform Evidence
CI / Conformance
```

Device Compatibility 还必须满足 Adapter Contract Tests / BICTS 等设备侧证据。

---

## 10. Device Adapter / OEM Port 的治理边界

Device Adapter Contract 定义：

> **一个设备接入 Baga Ink 必须提供什么。**

它不要求 Baga 重写已有 OS / Vendor SDK / Homebrew / Mature Open-source 能力。

具体设备 Port SHOULD 尽量薄，优先复用已验证机制，并把：

```text
Model / Firmware differences
Capability Detection
Device Profile
Quirk Set
Error / Event Normalization
```

集中在 Port 层。

Reader/UI Framework、安装路线、KPM/MRPI、Build Tooling 不得因为“和设备有关”就被塞进 Device Adapter Root Contract。

---

## 11. License 与第三方来源

Baga 自研内容默认使用 Apache License 2.0，除非文件/目录明确声明其他许可证。

第三方代码和组件保持自己的上游许可证；Baga 不通过仓库总许可证重新许可 KOReader、FBInk、KPM 等项目。

发行产品必须记录真实依赖、版本、来源、Digest、License 与 Patch Set。

正式入口：

```text
LICENSE
NOTICE
THIRD_PARTY_NOTICES.md
```

涉及 GPL / AGPL 或其他具有额外分发义务的集成方式时，许可证合规属于 Release Gate，而不是发布后的补文档工作。

---

## 12. Commit / Tag / Release

Commit 保存可追踪历史，Commit Subject SHOULD 使用英文并描述真实变化，例如：

```text
docs: migrate device adapter standard
spec: add publisher identity schemas
feat: add IKP signature verifier
test: add invalid IKP corpus
```

Tag / Release 用于正式阶段基线，例如未来：

```text
standards-v0.1
ikp-v1.0
platform-v0.1
sdk-v0.1
```

历史版本应通过 Git Commit / Tag / Release 恢复，不靠永久 Feature Branch。

---

## 13. 完成一项重要工作前的检查

至少确认：

```text
[ ] 有效代码进入 PR
[ ] 相关 Tests / CI 通过
[ ] 架构变化进入对应 Standard / Design
[ ] 外部依赖事实进入 Public Docs
[ ] 当前状态更新到 Status
[ ] 必要 Compatibility / Device Evidence 已记录
[ ] Branch 不包含 main 之外的唯一长期知识
[ ] License / Third-party provenance 没有被破坏
```

---

## 14. 最终原则

Baga Ink 是一个希望由不同国家、不同组织、不同设备厂商、不同 AI 工具长期维护的项目。

因此项目必须优化成：

> **读仓库，而不是读人的记忆。**

进一步说：

> **读 `main` 中的 Code + Machine Spec + Tests + Approved Public Docs，而不是读 Branch 森林和历史聊天。**
