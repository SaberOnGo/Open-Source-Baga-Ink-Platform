# 文档国际化与本地化规范

> **文档级别：项目治理规范**  
> **语言：简体中文（`zh-CN`）**  
> **状态：Governance Baseline v0.1**  
> **日期：2026-08-23**  
> **对应英文版：`docs/en/governance/01_documentation-internationalization-policy.md`**

## 0. 目的

Baga Ink 未来面向不同国家、不同语言的开发者共同维护。因此，公共文档不能长期使用“一个文件里中文 + 英文混写、一个文件名里中文 + 英文都塞进去”的方式。

本规范目标：

- 中文维护者可以直接阅读和编写完整中文技术说明，不需要把全英文规范作为唯一工作入口；
- 国际开发者可以只进入英文目录，就能理解公开 Standards、Design、Reference Apps、Governance、Status；
- 中英文不能逐渐漂移成两套协议或两套架构；
- 机器规范、代码、测试、标识符、工具继续保持语言无关/英文；
- 海量工程 Task、调试记录、AI Execution Prompt 不需要浪费成本全部复制一份英文。

## 1. 语言目录结构

公共、长期正文统一使用：

```text
docs/en/
docs/zh-CN/
```

以下目录属于必须国际化的公共文档类别：

```text
standards/
design/
reference-apps/
governance/
status/
```

两个语言目录 SHOULD 保持相同的类别和稳定文档编号。

例如：

```text
docs/en/standards/07_baga-ink-device-adapter-specification.md
docs/zh-CN/standards/07_设备适配器规范.md
```

两份都代表 Standard 07，不是两套 Device Adapter Contract。

## 2. 同一个文档身份，不按语言分叉协议

中英文版本是**同一个逻辑文档的不同语言版本**。

任何一个语言版本都不得静默引入另一套：

```text
Architecture
Requirement
API Contract
Permission Rule
Compatibility Rule
Implementation Freeze
```

Baga 不把“英语”或“中文”单独定义成另一套语义权威。项目事实优先关系是：

```text
机器可读规范 / Schema / Test Vector / 可执行 Conformance Evidence
        ↓ 在覆盖范围内优先
已批准的项目语义决策 + 稳定 Document Identity
        ↓
该文档对应的英文版与中文版
```

如果某个纯文字语义还没有机器规范覆盖，而中英文描述发生冲突，则这是一个**未解决的文档缺陷**。在解决之前，该冲突点不能进入 Stable Release Baseline。

## 3. 首次迁移的临时例外

本项目已经存在大量历史中文文档，因此第一次国际化迁移期间，`docs/localization/catalog.json` 允许明确记录：

```text
migration-pending
translation-pending
```

这只是一次性迁移状态，不是以后长期允许中英文漂移的理由。

如果英文版尚未完成，必须明确写 Translation Pending；不得创建一个看起来像完整 Standard 的英文空壳，然后让国际开发者误以为内容已经可依赖。

一旦某个 Catalog Entry 进入：

```text
current
```

以后语义修改 SHOULD 在同一个 PR 中同步更新中英文两份。确实暂时无法同步时，Catalog 必须显式标记 counterpart 为 stale / pending；Stable Gate 不能把它视为已同步。

## 4. 文件名规则

### 英文公共文档

格式：

```text
NN_lowercase-kebab-case-name.md
```

例如：

```text
00_baga-ink-standards-index.md
07_baga-ink-device-adapter-specification.md
11_baga-ink-kindle-adapter.md
```

规则：

- 数字前缀是该类别中的稳定 Document Number；
- 英文描述使用 ASCII lowercase kebab-case；
- 文件名不包含中文；
- 不再使用“中文 + 英文”双份名称塞在同一个文件名中的方式。

### 简体中文公共文档

格式：

```text
NN_中文名称.md
```

例如：

```text
00_规范总览.md
07_设备适配器规范.md
11_Kindle适配规范.md
```

规则：

- 与英文 counterpart 使用相同编号；
- 说明性文件名以中文为主；
- `Baga Ink`、`Kindle`、`Android`、`IKP`、`SDK`、`API` 等稳定技术身份可以保留英文；
- 不再在中文文件名结尾重复追加一整段英文翻译，因为 `zh-CN` 目录已经明确了阅读语言。

## 5. 正文语言规则

英文文件 SHOULD 使用英文正文。只有在真实用户数据、原始专有名词、语言示例等情况下保留中文。

中文文件 SHOULD 用中文把技术逻辑讲清楚，但不要为了“全中文”而强行翻译稳定技术身份。以下术语优先保留其正式形式：

```text
Baga Ink Platform
Baga Ink API
Baga Device Adapter Contract
IKP
Capability
Permission
SQLite
Automerge
KOReader
FBInk
KPM
MRPI
```

可以在中文里解释这些词的含义，但正式标识符本身应保持可识别。

## 6. 机器规范与工程代码保持英文/语言无关

以下目录不按语言复制：

```text
spec/
reference/
tests/
tools/
.github/
platform/
sdk/
client/
```

以下内容 SHOULD 使用英文：

- 本地化正文目录之外的源码文件名与目录名；
- Code Identifier、Comment、Docstring；
- Public API / Module Name；
- JSON / YAML / TOML Key 与 Schema Identifier；
- Machine-readable Error Code；
- CLI Command / Flag；
- Test Name；
- Dependency Manifest；
- Commit Subject 与 Release Tag。

这样不同语言开发者仍然面对同一套工程接口。

## 7. 工程计划不要求全部双语

`docs/plans/` 是施工区，不是公开协议本身，因此不要求每个 Task、调试步骤、AI Prompt 都复制一份英文。

特别是：

```text
docs/plans/platform-ports/kindle/
```

可以继续保持中文优先，并保留当前便于你查找的双语语义文件名规则。

但必须遵守：

> **只要一个结论要成为外部实现者必须依赖的稳定事实，就必须进入已经本地化的 Standards / Design / Reference Apps / Governance / Status。不能只躲在中文 Task Design 或 AI Execution Prompt 里。**

## 8. 仓库根目录语言

为了国际开发者进入 GitHub 后能直接理解项目：

```text
README.md              → 英文默认入口
README.zh-CN.md        → 简体中文入口
CONTRIBUTING.md        → 未来默认英文贡献指南
CONTRIBUTING.zh-CN.md  → 对应中文贡献指南
AGENTS.md              → 英文 AI / Automation 指令
```

这些属于仓库约定文件，是“公共文档必须数字前缀”的明确例外。

## 9. Localization Catalog

```text
docs/localization/catalog.json
```

记录公共文档身份和迁移/同步状态。

每个 Entry SHOULD 至少包含：

```text
id
category
number
legacy_path              尚未迁移时
zh_cn_path
en_path
status
```

允许状态：

```text
migration-pending
translation-pending
current
stale
superseded
```

Catalog 是机器校验的一部分，不得为了掩盖缺失翻译而随意修改状态。

## 10. AI / Contributor 工作规则

任何 AI 或开发者在创建、移动、重命名公共文档之前 MUST 阅读本规范，并运行文档国际化 Guard。

如果环境可以运行仓库命令，创建新的公共文档 SHOULD 使用标准脚手架，而不是手工乱起路径。

强制校验：

```text
python3 tools/check_docs_i18n.py
```

CI MUST 拒绝：

- 在 Legacy 混合语言目录继续新增公共文档；
- 乱建 `english/`、`chinese/`、`cn/`、`zh/` 等语言目录；
- `docs/en/` 下出现中文混合文件名；
- `docs/zh-CN/` 继续使用“中文名 + 英文名”重复拼接；
- 同一维护文档中英文编号/类别不匹配；
- 把 Task / Prompt / 工作日志塞进 Standards 等公共规范区；
- Catalog 指向不存在、冲突或错误类型的路径。

AI 不得为了让错误结构通过 CI 而私自放宽 Guard、扩大例外或乱改 Catalog。

## 11. 未来增加其他语言

初始维护语言只有：

```text
en
zh-CN
```

未来如果增加 `ja` 等语言，必须先经过治理变更，并至少具备：

- 合法的 BCP 47 风格 Locale Directory；
- 明确的 Maintainer / Review Ownership；
- 必要的 Terminology / Localization Guide；
- Catalog 中明确的同步状态；
- CI 校验。

禁止在单个 Standard 下面临时乱建：

```text
english/
chinese/
cn/
zh/
```

## 12. 最终原则

> **公共项目知识按 Locale Tree 国际化；Baga Ink 仍然只有一套实现契约；施工计划可以保持维护者语言；机器接口保持英文/语言无关；任何语言版本都不能演变成隐藏的 Baga Ink Fork。**
