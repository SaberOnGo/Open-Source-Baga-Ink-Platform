# 文档国际化与本地化规范

> **文档级别：项目治理规范**  
> **Document ID：`governance.localization.01`**  
> **语言：简体中文（`zh-CN`）**  
> **状态：Governance Baseline v1.1**  
> **日期：2026-08-23**  
> **对应英文版：`docs/en/governance/01_documentation-internationalization-policy.md`**

## 0. 目的

Baga Ink 面向不同国家、不同语言的 Contributor 长期协作，因此长期 Localized Documentation 按 Locale Tree 维护，而不是把多种人类语言混合在同一个文件名或同一段正文中。

目标：

- International Contributor 可以从完整英文文档理解项目；
- 中文 Maintainer 可以直接使用完整简体中文技术文档；
- 不同 Locale Edition 不能逐渐漂移成不同 Protocol / Architecture；
- Machine-readable Contract、Code、Tests、Identifier、Tooling 保持共享并使用英文/语言无关形式；
- High-volume Operational Engineering Document 不要求为每个 Locale 全量复制；
- 所有被 Git 跟踪的 Documentation 都必须适合作为 Public Repository Content 对外阅读。

## 1. 永久 Locale Architecture

长期 Localized Prose 放在：

```text
docs/en/
docs/zh-CN/
```

受治理的 Localized Category：

```text
standards/
design/
reference-apps/
governance/
status/
```

早期中英混合 Public Directory 已废止，MUST NOT 重新出现。

## 2. 同一个 Document Identity，不按语言分叉 Protocol

中英文 Counterpart 是同一个逻辑文档的不同 Human-language Edition。

任何 Locale Edition MUST NOT 静默引入不同的：

```text
Architecture
Requirement
API Contract
Permission Rule
Compatibility Rule
Signing / Identity Rule
Distribution / Update Rule
Implementation Freeze
```

权威顺序：

```text
Machine-readable Spec / Schema / Test Vector / Executable Conformance Evidence
        ↓ 在覆盖范围内优先
Approved Project Semantic Decision + Stable Document Identity
        ↓
Maintained Locale Editions
```

如果 Maintained Locale 的 Prose Semantic 冲突，这是 Documentation Defect，MUST 在相关要求进入 Stable 前完成修正。

## 3. Stable Document Identity

`docs/localization/catalog.json` 记录每份 Localized Public Doc 的：

```text
id
category
number
en_path
zh_cn_path
status
legacy_path = null
```

同一 Category 内数字前缀属于 Document Identity 的稳定部分。

例如：

```text
docs/en/standards/07_baga-ink-device-adapter-specification.md
docs/zh-CN/standards/07_设备适配器规范.md
```

两份都代表 Standard 07。

## 4. 文件名规则

### English

```text
NN_lowercase-kebab-case-name.md
```

要求：

- 两位 Stable Number；
- ASCII lowercase kebab-case 描述名；
- 不包含中文字符；
- 不在同一个文件名重复“中文 + 英文”。

### 简体中文

```text
NN_中文名称.md
```

要求：

- 与英文 Counterpart 使用相同 Stable Number；
- 描述名以中文为主；
- Canonical Technical Identity 可以保留英文；
- 不追加冗余英文后缀，因为 Locale Directory 已经标明受众语言。

根目录 `README.md`、`README.zh-CN.md`、`CONTRIBUTING.md`、`CONTRIBUTING.zh-CN.md`、`AGENTS.md` 等在 Filename Structure 上单独治理，但仍受 Repository-wide Public Writing Rule 约束。

## 5. 正文语言与技术术语

英文 Localized File SHOULD 使用英文解释。

简体中文 Localized File SHOULD 使用中文解释，同时保持稳定技术身份可识别，例如：

```text
Baga Ink Platform
Baga Ink API
Baga Device Adapter Contract
IKP
Capability
Permission
SQLite
Automerge
KOReader
FBInk
KPM
MRPI
BICTS
```

Identifier MUST NOT 被机械翻译成第二套技术词汇或不兼容 API Name。

Canonical Terminology 由：

```text
docs/localization/terminology.json
```

机器记录。

## 6. Public Writing Voice 适用于整个 Repository

这个 Repository 是 Public Repository。任何被提交并由 Git 跟踪的 Documentation File 都属于对外材料，不论它是 Standard、Governance、README、Engineering Plan、Task Design 还是 AI Execution Prompt。

Localization Requirement 与 Publication Requirement 是两个不同问题：

```text
Localized Standards / Design / Reference Apps / Governance / Status
        → 按 Governance 要求维护 Locale Counterpart

Operational Engineering Plans under docs/plans/
        → 不要求为每个 Locale 全量镜像

两类文档
        → 都是 Public、Third-party-readable、Publication-quality Prose
```

所有 Tracked Documentation MUST 在没有 Private Chat Context 的情况下能够独立理解，并使用适合实际 External Audience 的表达。

Public Prose MUST NOT 包含：

- 对 Repository Owner 的个人建议或聊天式回复；
- 引用私人对话中的“前面 / 刚才 / 上面讨论”等上下文；
- 关于某种措辞是否会让用户、Developer 或 OEM 反感、害怕、愿意或不愿意参与的私人策略判断；
- Confidential Monetization Rationale、Negotiation Tactics、未公开 Pricing Strategy 或其他内部 Business Reasoning；
- `我建议`、`我们认为` 等把私人咨询过程直接写进公共正文的 Authorial Phrase；项目 Requirement、Decision、Policy 与 Rationale 应直接陈述。

Operational Document 可以使用面向其真实 Public Role 的命令式 Engineering Instruction，例如 `Contributor MUST`、`Task MUST`、`OEM Port SHOULD`。

Confidential Strategy 应保存在 Public Git Tracking 之外，例如被忽略的本地 `private/` 目录或独立 Private Repository。

Repository-wide Writing Validation：

```text
python3 tools/check_public_writing.py
```

## 7. Machine / Code Surface 保持英文或语言无关

以下目录不按 Locale 复制：

```text
spec/
reference/
tests/
tools/
.github/
platform/
sdk/
client/
```

以下使用英文：

- Localized Prose Tree 之外的 Source File / Directory Name；
- Code Identifier、Comment、Docstring；
- Public API / Module Name；
- JSON/YAML/TOML Key 与 Schema ID；
- Machine Error Code；
- CLI Command / Flag；
- Test Name；
- Dependency Manifest；
- Commit Subject / Release Tag。

## 8. Operational Engineering Plans

`docs/plans/` 是 Engineering Work Area，不是 Normative Public Protocol Surface。

不要求把每份 Task Design / AI Execution Prompt 复制成多个 Maintained Locale。

特别是：

```text
docs/plans/platform-ports/kindle/
```

可以继续中文优先，并保持严格可搜索的双语 Filename Convention。

这不代表 `docs/plans/` 是 Private。所有 Plan 都公开可见，MUST 满足 Repository-wide Public Writing Rule。

只要某个 Stable Design Fact 成为 External Implementer 必须依赖的事实，就 MUST 提升回 Localized Standards / Design / Reference Apps / Governance / Status，不能只在 Maintainer-language Task / Prompt 中保持权威。

## 9. Maintained Pair 同步规则

Catalog 中 `status = current` 的文档，Semantic Change SHOULD 在同一个 Reviewed PR 中同步修改所有 Maintained Locale Counterpart。

如果无法立即同步，Catalog MUST 显式标记 Pending / Stale；Stable Release Process 不能把该 Pair 视为同步完成。

`superseded` 用于明确不再作为当前 Authority 的历史兼容入口。

## 10. Repository 首页语言模型

国际项目默认入口：

```text
README.md              → English default
README.zh-CN.md        → 简体中文
CONTRIBUTING.md        → English default
CONTRIBUTING.zh-CN.md  → 简体中文
AGENTS.md              → English AI / Automation Instructions
```

README Locale Registry：

```text
docs/localization/readme-languages.json
```

所有 Current README Locale MUST 展示同一组受治理的 Language Switch Entry。

## 11. 未来新增 Locale

未来增加 `ja`、`de`、`fr`、`ko` 等 Locale，必须先通过明确 Governance Change。

Maintained Locale 至少需要：

- 合法 BCP 47-style Locale Tag；
- Root README Translation 时的 Registry Entry；
- `docs/<locale>/` 文档树；
- Maintainer / Review Ownership；
- 必要 Glossary / Terminology Policy；
- Catalog 中明确 Synchronization State；
- CI Validation。

禁止创建：

```text
chinese/
english/
cn/
zh/
docs/standards/en/
```

这类平行结构。

## 12. AI / Contributor Hard Gate

创建、重命名、移动、翻译或修改任何 Tracked Documentation 前，Contributor / AI MUST 同时遵守相应 Structure Rule 与 Repository-wide Public Writing Rule。

Localized Public Doc 优先使用：

```text
python3 tools/new_localized_doc.py ...
```

Localized Public Doc 完成前必须通过：

```text
python3 tools/check_docs_i18n.py
```

所有 Tracked Documentation 必须通过：

```text
python3 tools/check_public_writing.py
```

CI 至少拒绝：

- 重新创建旧中英混合 Public Directory；
- 非法 Locale Path；
- 非法英文 / 中文 Filename；
- 未登记 Catalog 的 Localized Public Doc；
- Duplicate Document ID / Target Path；
- Migration 完成后出现 Non-null `legacy_path`；
- `current` / `superseded` 缺失 Maintained Counterpart；
- 未经 Governance 引入的 Nested Category Structure；
- Tracked Markdown 中已知的 Private-discussion / Internal-strategy Writing Pattern。

AI MUST NOT 为了让 Invalid Content 通过而削弱 Guard、扩大 Allowlist 或修改 Catalog / Validator Rule。

## 13. 最终规则

> **Localized Project Knowledge 使用受治理 Locale Tree；Protocol 与 Implementation Contract 始终只有一个项目；Operational Engineering Plan 可以保留 Maintainer Language，但仍然是 Public Documentation；Machine Surface 保持共享并使用英文/语言无关形式；所有 Tracked Document 都面向 External Repository Audience。**
