## 0. 目的

Capability Registry 定义：

> **设备或 Platform 具有什么跨设备能力，App 应以什么稳定语义查询。**

它不是开源库、Standard Library、数据库或内部 implementation 名称清单。

正式正文只列当前注册的 Capability 与当前有效规则。

---

# 1. 命名规则

Capability 使用小写点分层级：

```text
category.feature
category.feature.variant
```

当前示例：

```text
display.partial_refresh
input.pen.pressure
light.frontlight.temperature
reader.anchor
```

规则：

- MUST 使用小写 ASCII；
- MUST 使用 `.` 分层；
- MUST 不包含厂商品牌名；
- MUST 不包含内部实现库名；
- MUST 描述跨设备能力语义，而不是 Library/API 名；
- 已发布稳定 Capability SHOULD 不轻易重命名。

SQLite / `lsqlite3` 属 Baga Lua Profile Standard Library；Automerge 属 Adopted Foundation。二者都不进入 Capability Registry。

---

# 2. Capability 与 Permission

Capability：设备 / Platform **能不能做**。

Permission：App **允不允许使用某资源/用户数据**。

例如：

```text
Capability: network.wifi
Permission: network
```

授权规则见 Permission Model。

---

# 3. Base Profile

所有 Baga Ink Compatible 设备 MUST 提供或正确降级：

```text
display.basic
input.navigation
storage.app_sandbox
power.sleep_wake
platform.lifecycle
```

这些保证基本 IKP 可显示、操作、保存状态、休眠恢复。

Standard Libraries 的可用性由 **Baga Lua Profile / Platform version** 定义并由 BICTS 验证，不通过 Device Capability 表达。

当前 SQLite 标准库通过：

```lua
require("lsqlite3")
```

提供。

# 6. Network

```text
network.available
network.wifi
network.http
network.https
network.connectivity_events
```

这些表示 Platform 可提供对应网络能力，不规定内部 HTTP/TLS library。

Automerge sync protocol（若某业务采用）属于 Local-first 数据同步语义，不是网络硬件 Capability。

---

# 7. Storage

## `storage.app_sandbox`

Platform 可以为每个 App 提供受保护的逻辑沙箱。Base Compatible MUST 支持。

## `storage.user_library`

Platform 可以桥接设备现有用户书库，并通过 `baga.library` 暴露。

## `storage.user_files`

Platform 可以提供用户选择/授权文件访问。

## `storage.external`

存在可访问扩展存储，例如 SD 卡。

SQLite database 作为 App sandbox 中的 Standard Library 使用场景，不注册独立 Device Capability。

# 12. Reader

Reader 能力属于 Platform 提供的高级能力，不要求 Device Adapter 本身直接实现全部 Reader 逻辑。

```text
reader.open
reader.search
reader.selection
reader.highlight
reader.note
reader.position
reader.anchor
```

App 不查询 KOReader/MuPDF/CREngine 名称。

## 12.1 `reader.anchor`

表示 Reader 可以：

```text
create_anchor
serialize/pass opaque anchor
goto_anchor
resolve_anchor
```

语义：

- 不限定 EPUB；
- 不限定 PDF；
- 不要求所有格式共用一种底层 locator；
- 实现可以复用 KOReader XPointer-like position、PDF positions/boxes 或其他成熟机制；
- App 不解析 Reader-private fields；
- approximate recovery 必须明确，不冒充 exact。

`reader.anchor` v0.4 仍为 provisional，待 Kindle/Android、多格式 BICTS 验证后再升级 stable。

# 14. Capability 状态

```text
experimental
provisional
stable
deprecated
removed
```

标准语义一旦 stable，应有合理兼容周期。

---

# 15. Capability 注册流程

新增 Capability 前必须：

```text
需求出现
  ↓
判断是否只是成熟 Standard Library 问题
  ├─ 是 → 按 Standard 13 处理
  └─ 否 → 判断是否是真实跨设备 Platform/Device 能力
  ↓
定义中立语义
  ↓
验证不同设备/实现路径
  ↓
加入 experimental/provisional
  ↓
API / Adapter / BICTS
  ↓
稳定后 stable
```

厂商私有 API 名、内部 Library 名以及具体开源项目名不得直接成为标准 Capability 名称。

---

# 16. Vendor Extension

标准化前 MAY 使用受控私有实验命名：

```text
x.vendor.feature
```

但不得用于 Universal stable certification。

# 18. 核心原则

> **Capability Registry 是跨设备能力语义契约，不是成熟开源库的包装注册表。**

SQLite、Automerge、KOReader 等分别由 Standard Library、Adopted Component 或 Platform implementation 的正式边界管理。
