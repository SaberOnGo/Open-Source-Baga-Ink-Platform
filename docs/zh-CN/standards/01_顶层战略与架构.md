## 0. 本文档地位

本文档定义 **Baga Ink** 的长期战略边界、平台定位、生态命名、应用模型、开发模型、设备兼容模型和反碎片化原则。

它是 Baga Ink Standards 中最高层级的技术战略文档。

后续所有 Standards、SDK、Platform Core、Device Adapter、Baga Ink Client、Baga Ink Market、LifeBook Reference App 与未来 OEM Adapter 都不得静默违背本文。

### 0.1 规范关键词

- **MUST**：平台级硬要求；
- **SHOULD**：默认应遵守，除非有明确合理例外；
- **MAY**：允许的实现选择。

### 0.2 架构术语极简原则

Baga Ink 的设备端平台统一理解为：

```text
Baga Ink Platform
├── Baga Ink Platform Core
├── Embedded Lua Interpreter
├── Baga Lua Profile
├── Baga Ink API
├── IKP Package Manager
└── Baga Ink Device Adapter
```

Lua Interpreter 是 Platform Core 内部嵌入/复用的轻量执行能力，不定义成需要用户、App 开发者或设备厂商额外安装、理解和维护的独立重量级产品层。

正式架构不使用“为了运行 App 而必须再安装一层重量级中间系统”的表述。

### 0.3 成熟实现复用原则

Baga Standards 负责定义：

```text
公开 API
跨设备语义
Capability / Permission
兼容性与安全边界
Baga Lua Profile / Standard Libraries
```

但**不规定每个 Platform implementation 内部必须拆成多少层软件，也不要求把已经成熟的能力重新实现一遍**。

Platform Core、Device Adapter 与官方 Reference implementation 在实现某项能力前，SHOULD 先评估：

```text
成熟
活跃维护
许可证可接受
已有真实设备/生产验证
```

的现成组件；只要不破坏 Baga 公共 Contract，就 MAY：

```text
整项目采用
组合采用多个组件
只抽取稳定模块
直接采用成熟上游 API
复用现有 protocol / data format / algorithm
包装现有设备机制
```

如果某成熟通用库已经提供了**跨平台、稳定、广泛采用的开发者抽象**，Baga SHOULD 优先把它直接采用为：

> **Baga Lua Profile Standard Library / Adopted Component**

而不是再发明一个功能更弱的 Baga 私有 wrapper。

当前正式原则性例子：

```text
SQLite + lsqlite3
→ 作为 Baga Lua Profile Standard Database Library
→ App 直接使用成熟 SQLite / SQL 语义

Automerge core
→ 作为 Local-first / CRDT 优先基础
→ 可整体采用，也可拆用 document/merge、binary、sync、C FFI、patch/cursor 等模块

KOReader / koreader-base / FBInk
→ Kindle Platform / Adapter 可大量复用的成熟实现来源
```

采用这些项目时：

- MUST 不因为“用了一个库”就自动增加新的 Baga 公共架构层；
- MUST 不仅因为库存在而发明 `Provider`、`Engine`、`Runtime` 等层级；
- MUST 不默认把上游库的私有对象、术语、内部文件格式或私有 API 暴露成 `baga.*` 标准；
- MAY 在标准明确规定后，把成熟上游 API / protocol / format 直接作为 Baga Lua Profile Standard Library；
- MUST 不要求 IKP App 理解底层具体实现；
- MUST 不绕过 BICTS、Permission、Sandbox 与 Compatibility 要求。

原则：

> **先复用成熟能力，再补 Baga 所需的薄抽象；标准化语义，不标准化内部软件层数。**

成熟库采用、版本冻结和公共 API 暴露边界由 Standard 13 规定。

正式 Standards / Reference Apps 只保留当前采用架构；历史方案由 Git 保存。

# 1. 一句话定义

> **Baga Ink Platform 是一个面向 Kindle 与 Android 墨水屏设备的统一、轻量、跨设备应用平台。**

目标不是做一个单独的墨水屏 App，而是：

> **把高度碎片化的 Kindle Homebrew 与 Android E-Paper 设备，逐步统一成一个第三方开发者可以稳定依赖的应用平台。**

---

# 2. 要解决的核心问题

墨水屏生态高度碎片化：

```text
Kindle
├── 多代硬件
├── 多代 Firmware
├── Homebrew / KUAL / MRPI / KOReader 等基础设施
└── Display / Input / System 行为差异

Android E-Paper
├── iReader
├── BOOX
├── Bigme
├── Hanvon
├── Moaan
└── 其他 Vendor
    ├── Android 版本不同
    ├── Refresh API 不同
    ├── Pen SDK 不同
    └── Power / Frontlight / System API 不同
```

如果每一个 App 都分别适配每一台设备，那么碎片化会永久扩散到 App 生态。

Baga Ink 的战略是：

> **把碎片化压缩到 Device Adapter 以下，而不是让碎片化扩散到每个应用。**

```text
                   Third-party IKP Apps
                          │
                          ▼
                Baga Ink App Standard
                          │
                          ▼
            Baga Ink SDK / Baga Ink API
                          │
                          ▼
                Baga Ink Platform Core
                          │
                          ▼
                Baga Ink Device Adapter
                     ┌────┴────┐
                     │         │
                     ▼         ▼
                  Kindle    Android E-Paper
```

核心规则：

> **App 不适配设备；设备通过 Baga Device Adapter 适配 Platform。**

内部复用 KOReader、SQLite、Automerge、FBInk 等实现时，不在这张公共架构图上增加新的公共层。

Baga Lua Profile Standard Library 同样不是新增层，它表示：App 环境中可直接使用成熟通用库。

# 5. Baga Ink Platform 边界

Baga Ink Platform 包含：

- Platform Core；
- Embedded Lua Interpreter；
- Baga Lua Profile；
- Baga Lua Profile Standard Libraries；
- Baga Ink API；
- App Lifecycle；
- UI / Display / Input / Storage / Library / Network / Power / Reader / Sync；
- Capability Model；
- Permission / Sandbox；
- IKP Package Manager；
- Device Adapter；
- Compatibility hooks。

这些共同构成一个轻量设备端 Platform。

**Baga Ink Platform 不包括 Baga Ink Client，也不包括 Baga Ink Market。**

具体能力内部可复用成熟项目；这些项目本身不成为新的 Baga 公共层。

# 6. Universal App 模型

## 6.1 第一官方应用语言

第一阶段正式语言：

> **Lua / Baga Lua Profile**

Baga Lua Profile 定义：

- 允许的 Lua language features；
- 基础标准库；
- Adopted Standard Libraries；
- `baga.*` API；
- 生命周期；
- 安全限制；
- 禁止的系统逃生能力。

Kindle implementation MAY 复用 KOReader / related project 已验证的 Lua / LuaJIT 环境；Android Platform APK MAY 嵌入轻量 Lua Interpreter。

第三方 App 不依赖解释器来源。

当前 Stable Standard Library：

```text
lsqlite3
→ 直接暴露成熟 SQLite / SQL 语义
```

当前 Adopted Foundation：

```text
Automerge core
→ Local-first / CRDT 优先基础
→ developer-facing Lua binding 尚未冻结
```

详细规则见 Standard 13。

## 6.2 为什么不把 Kotlin / Java 作为 Universal App 边界

Android 天然支持 Kotlin / Java，但 Kindle 不是 Android。

如果把 Kotlin / Java 作为跨设备 App 语言，会迫使旧 Kindle 获得更重实现层，违背 Baga 的轻量和存量设备策略。

## 6.3 Rust 的定位

Rust 非常适合：

```text
Platform Core
network / sync
parser
security-sensitive components
Device Adapter
Automerge core / C FFI integration
```

Platform 内部 MAY 使用 Rust、C/C++、Kotlin/Java、JNI、Shell 或其他设备适合的语言。

> **统一发生在第三方 App 边界，不发生在所有底层实现语言。**

内部 Library Selection 同理：内部组件不创造第三方 App 必须理解的新边界。

# 7. IKP：跨设备 App 分发单位

Universal App 包格式：

> **IKP / `.ikp`**

示例：

```text
lifebook.ikp
rss-reader.ikp
notes.ikp
```

同一个 IKP 目标上运行于 Kindle 和 Android E-Paper（Capability 允许时）。

典型内容：

```text
manifest.json
main.lua
src/
assets/
locales/
signature/
```

Universal IKP MUST 不把这些作为普通业务执行依赖：

```text
设备私有 Native Binary
Android APK / DEX business logic
Kindle Shell Bridge
BOOX / iReader private SDK wrapper
另一份 Lua Interpreter
另一份 Device Adapter
另一份 Platform Core
```

原则：

> **App code/resources 属 IKP；Device Compatibility 和 Shared Platform Capability 属 Baga Ink Platform。**

Platform 提供的 Standard Libraries 不需要每个 IKP 再携带一份。

# 8. Capability-first 开发模型

Universal App MUST 查询“设备能做什么”，而不是“设备是什么品牌”。

正确：

```lua
if baga.device.has("input.pen") then
    enable_pen_ui()
end

if baga.device.has("display.fast_refresh") then
    enable_fast_interaction()
end
```

错误：

```lua
if vendor == "BOOX" then ... end
if device == "Kindle" then ... end
```

正式 Capability 只由 Standard 04 维护。

Base Profile：

```text
display.basic
input.navigation
storage.app_sandbox
power.sleep_wake
platform.lifecycle
```

典型 Optional Capability：

```text
display.partial_refresh
display.fast_refresh
display.color
input.touch
input.pen
input.pen.low_latency
input.physical_page_key
network.wifi
light.frontlight
audio.output
bluetooth.available
```

SQLite / lsqlite3 是 Standard Library，不是 Hardware Capability。

---

# 9. Permission 与 Capability 分离

Capability：设备 / Platform **能不能做**。

Permission：App **可不可以访问**。

例如：

```text
Capability: network.wifi
Permission: network
```

Permission 在 Manifest 预声明，并遵守最小权限原则；Standard 05 定义具体规则。

# 10. Baga Ink API

公开 namespace：

```lua
baga.api
baga.app
baga.ui
baga.display
baga.input
baga.device
baga.storage
baga.library
baga.network
baga.power
baga.reader
baga.sync
baga.permissions
baga.log
```

结构化关系数据直接使用 Baga Lua Profile Standard Library `lsqlite3` / SQLite。

因此 Developer Environment 有两个不同概念：

```text
baga.*
→ 统一 Device / OS / Platform 差异

lsqlite3 / adopted libraries
→ 直接提供成熟通用软件能力
```

Baga MUST 不提供任意 Shell、Android Context、Direct Vendor SDK 的 Universal escape hatch。

新增能力流程：

```text
真实需求
  ↓
成熟通用库已解决？
  ├─ 是 → Standard Library / Adopted Component
  └─ 否，且属于 Device/Platform 差异 → Capability / Baga Ink API
  ↓
Platform implementation
  ↓
BICTS
```

Platform 内部 MAY 直接复用成熟项目，不需要机械增加 `Provider` / `Engine` 层。

# 11. UI Strategy

Baga UI 不是 Mobile UI 的机械移植。

核心：

- High contrast；
- page-oriented / stable layout 优先；
- Focus 为 First-class；
- Touch / Physical Navigation 在语义层统一；
- 少 Animation；
- 少 Full Refresh；
- Dirty Region；
- App 表达 Refresh Intent，Platform 选择真实刷新机制；
- Color / Pen / Fast Refresh 属 Progressive Enhancement。

详见 Standard 09。

# 12. Device Adapter Strategy

```text
Baga Ink Platform Core
        │
        ├── Kindle Adapter
        └── Android E-Paper Adapter
             ├── Generic Android
             ├── BOOX specialization
             ├── iReader specialization
             ├── Bigme specialization
             ├── Hanvon specialization
             └── future vendor specialization
```

Adapter 吸收：

```text
Display / Refresh
Input
Storage Mapping
Lifecycle
Power
Network
Frontlight
Pen
Audio
Bluetooth
Device Quirks
Firmware differences
```

Adapter MUST 不成为第二套 App API。

Android Adapter 内 Vendor-specialized provider 只是 private capability implementation detail，不意味着每个 `baga.*` 都要先再包一层 Provider。

# 13. Kindle Strategy

现有 Kindle Homebrew 生态是要复用的基础，不是 Baga 要从头替代的对象。

Baga SHOULD 复用成熟能力，例如：

```text
KOReader device / reader / display / input / annotation knowledge
koreader-base / MuPDF / CREngine reader foundations
KUAL / PEKI-class launch/bootstrap capability where applicable
MRPI / KPM / Hotfix-class install/Homebrew foundation
FBInk / framebuffer display capability
Kindle system-service bridge
KOReader existing libsqlite3
KOReader internal lua-ljsqlite3 where it remains implementation detail
Baga IKP standard SQLite binding: lsqlite3
Automerge core when Local-first / CRDT is actually needed
```

这些都是 **Baga Ink Platform on Kindle 内部实现 / Standard Library supply choices**，不自动变成公共架构层。

第三方 IKP App 只看到：

```text
Device Capability → baga.*
Relational Database → require("lsqlite3")
```

App 不需要知道 KOReader 内部是否仍使用其他 SQLite Lua Binding。

Kindle Adapter Standard 与 Jailbreak / Installation Route Database 必须分离；Jailbreak Route 随 Device / Firmware 变化，但 Platform Contract 必须稳定。

# 14. Android E-Paper Strategy

概念：

```text
Baga Ink Platform.apk
        │
        ├── Platform Core
        ├── Baga Ink API
        ├── Baga Lua Profile / Standard Libraries
        ├── Embedded Lua Interpreter
        └── Android E-Paper Adapter
        │
        ▼
      *.ikp
```

Generic Android 提供 Common Android Capability；Vendor Specialization 补 E-Paper Refresh、Pen、Frontlight 等私有能力。

Android Version / Vendor fragmentation 必须停在 Adapter 之下。

Android implementation 同样 SHOULD 最大化复用成熟 System / Open-source Capability，而不是为了内部统一外观重写 Database、Network、Document Engine、Sync。

Platform 为 IKP App 固定一套可预测 SQLite runtime / lsqlite3 profile，不依赖随机 OEM SQLite Version。

# 15. Baga Ink Client Strategy

Baga Ink Client 是计划中的 Windows/macOS 设备入口。

核心流程：

```text
Connect Device
  ↓
Detect Model / Firmware / System
  ↓
Query Compatibility / Installation DB
  ↓
Compatible / Experimental / Unsupported
  ↓
Safely install / repair / update Baga Ink Platform
  ↓
Install LifeBook / Market Apps
```

硬规则：

- 不删除用户书籍；
- 不删除用户笔记；
- Factory Reset 不是标准解决方案；
- Failure SHOULD recover where practical；
- 未验证组合不得宣传为 Supported。

# 17. Compatibility 必须可验证

设备不是因为“LifeBook 启动过一次”就 Compatible。

正式 Compatibility 依据：

> **Baga Ink Compatibility Test Suite / BICTS**

Compatibility Statement 绑定：

```text
Device Model
+ Firmware / OS Range
+ Platform Version
+ Adapter Version
+ Compatibility Standard Version
+ BICTS Version
```

状态：

```text
Baga Ink Compatible
Experimental
Unsupported
```

详见 Standards 08 / 10。

Standard Libraries 也要验证一致性，包括 lsqlite3 行为、SQLite compile profile 与 sandbox。

# 18. LifeBook 的战略角色

LifeBook 是：

> **Baga Ink Flagship Reference App。**

LifeBook 必须遵守第三方 Universal App 同样的核心规则，不能靠别人拿不到的 Privileged Shortcut 来“证明”平台可用。

目标：

```text
same lifebook.ikp
      │
      ├── Kindle
      └── Android E-Paper
```

LifeBook 暴露新能力缺口时，先判断：

```text
Device / Platform Difference → baga.* / Capability
Mature General-purpose Capability → Standard Library / Mature Component
```

不要增加 Vendor-specific Business Branch 或重复成熟基础设施。

# 19. Open Ecosystem, Controlled Boundary

Baga SHOULD 允许：

- Third-party IKP Apps；
- Third-party Device Adapter contributions；
- OEM-maintained Adapters；
- Controlled Capability Providers；
- Third-party SDK / Platform Core contributions；
- Standard Library integration / Compatibility Test contributions。

开放不等于没有标准。

核心原则：

> **下层允许多样，上层保持统一。**

```text
App Layer          高统一
API Layer          高稳定
Standard Libraries 直接沿用成熟语义
Capability Layer   标准化扩展
Adapter Layer      允许设备差异
OS Layer           可以完全不同
Hardware Layer     可以完全不同
```

内部 Dependency Graph / Source Directory Layout 不属于公共 Layer Model。

# 22. Non-goals

Baga Ink 当前不试图：

1. 自建完整 E-Paper OS；
2. 替代 Android；
3. 替代 Kindle OS；
4. 重写整个 Kindle Homebrew 生态；
5. 强制所有底层代码使用 Lua；
6. 强制 Platform Core 只用一种语言；
7. 允许 Universal App 任意逃生到 Host System；
8. 为每个设备品牌维护独立 App Business Logic Fork；
9. 把 LifeBook 私有需求自动升级成 Platform Standard；
10. 发明一个必须额外维护的重量级中间 Runtime 产品；
11. 仅因为使用一个开源库就创造新的公共架构层；
12. 在有成熟、License-compatible、已验证实现时，仅为了“全自研”重写 Reader / Database / Merge Algorithm / Device Infrastructure；
13. 把 SQLite 再包装成更弱的 Proprietary KV / Collection Database；
14. 因为 Automerge 很优秀就要求所有数据 CRDT 化，或机械照搬 `automerge-repo` 的所有层。

# 23. Strategic Success Criterion

最终必须回答：

> **第三方开发者是否可以只学习一套 Baga Ink SDK / Lua Profile，写一个 `.ikp`，就在 Kindle 与多个 Android E-Paper 设备上运行，而不需要学习每个设备 Private Implementation？**

成熟通用能力继续站在成熟生态上：

```text
Relational Data → SQLite / lsqlite3
Reader → Baga Reader API，内部复用 KOReader 等成熟 Engine
Local-first CRDT → 真正需要时优先 Automerge core
```

如果开发者仍然要分别维护 Kindle / BOOX / iReader / Bigme 等 Business Code Tree，那么 Baga 就没有真正成为 Application Platform，而只是另一个聚合层。

---

# 24. 长期方向

Baga Ink 目标成为：

> **运行在 Existing OS 之上的 Lightweight E-Paper Application Platform。**

不要求所有设备使用同样 Hardware、同样 OS 或同样 Implementation Language。

只要求一件最重要的事：

> **第三方 App 面对同一个稳定 Platform，并能直接复用成熟通用软件生态。**
